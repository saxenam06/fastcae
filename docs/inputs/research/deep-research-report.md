# Related Projects & Methods

We reviewed each project and paper and grouped them by relevance:

- **Generative CAD Models:** *Hierarchical Neural Coding (HNC-CAD)* is a recent ICML 2023 model that generates diverse CAD variants from a given base design, using a three-level latent code tree. It illustrates how to produce many geometry variations from one input (see Fig.5 in Xu et al. 2023). *SketchGraphs* is a large dataset of 15M 2D sketches with constraint graphs, enabling sketch-based generative or constraint-solving models.  
- **B-Reps and Graph Representations:** Several works build graph representations of B-rep CAD data. For example, the *CAD Feature Detection* demo uses [occwl](https://github.com/AutodeskAILab/occwl) to convert STEP/B-rep into a graph input for UV-Net. *CADNet* (Colligan et al. 2020) and *BRepMFR* (Zhang et al. 2024) use graph neural networks on B-rep face graphs for machining-feature recognition. These show how to encode topology and geometry into a GNN for classifying faces (holes, pockets, etc.).  
- **Feature Recognition Networks:** *AAGNet* (Wu et al. 2024) is a GNN that recognizes and localizes machining features (holes, bosses, fillets) on B-reps. *FilletRec* (Gao et al.) focuses specifically on identifying fillet features using intrinsic geometry features. All these are examples of multi-task GNNs applied to B-rep data for automated feature detection.  
- **Differentiable/Implicit CAD:** *cadjoint* is a new framework for “differentiable implicit CAD” using JAX, allowing one to edit a CAD design via code/GUI and run gradient-based optimizations. It suggests a way to integrate constraint solving and continuous optimization directly in CAD.  
- **Agentic/LML Approaches:** *ScadLM* is an attempt to use an LLM agent with OpenSCAD to generate models from text. It was not very successful, but it illustrates an agent-based CAD pipeline using a token-based solid modeling language.  

Each project targets a piece of the pipeline. In particular, **graph-based feature recognition** (AAGNet, FilletRec, BrepMFR, CADNet, UV-Net) can help analyze B-rep geometry; **generative models** (HNC-CAD, SketchGraphs, ScadLM) can propose new designs; and **differentiable CAD** (cadjoint) points to advanced optimization of shapes under constraints.

# Methods for B-Rep Parsing and Feature Recognition

**Graph representations:** To feed CAD data into neural nets, many tools convert the B-rep into a graph. For example, the CAD feature demo uses PythonOCC (a Python wrapper of OpenCASCADE) with the *occwl* helper to build an adjacency graph from the STEP model. This graph has faces/nodes and edges for shared edges. Similar pipelines underlie AAGNet, BRepNet and CADNet. We would adopt a graph construction (e.g. via occwl or custom PythonOCC) that produces node features (face normals, area, curvature, etc.) and adjacency (edge or vertex connectivity). 

**Feature detection networks:** Pretrained networks can then label graph nodes. For instance, AAGNet takes this geometric adjacency graph (gAAG) and outputs face-level feature classes. FilletRec likewise builds a pose-invariant GNN to recognize fillet faces. BrepMFR uses a transformer-GNN to label 24 machining features on B-rep graphs. We would use or adapt these models (and the public MFCAD or MFInstSeg datasets) to detect features on our gearbox housing (holes, ribs, fillets, bosses, etc.). This gives a robust way to implement operator pre/post-conditions and check that faces of interest (bearing seats, bolt holes) are present and correctly shaped. 

**Semantic identity via ML:** Critically, these networks can help track geometry entities across edits. For example, after a Boolean or rib-adding operation, the algorithm can re-run a GNN to re-label faces. If the “bearing seat” face is missing or altered beyond tolerance, this would flag a contract violation. In effect, face identity is partly encoded by the neural labels (e.g. any face classified as “bolt hole” vs “pocket” vs “surface”). While not foolproof, combining graph isomorphism checks with label matching (e.g. the faces that remain labeled as [BEARING_SEAT] must match the original’s axis/dimensions) would implement the **stable interface identity** from the design contract. 

# Mapping Methods to Pipeline Gaps

Here we propose how to integrate these ML/AI tools to fill the identified gaps:

- **Geometry operator contracts:** We need formalized contracts (pre/post conditions) for each CAD edit. Here, **feature detection networks** are invaluable for validating contracts. For example, a learned model can verify that an “AddRib” operation did not break a bearing seat or create a thin wall. After applying an operator, run a GNN (e.g. AAGNet/FilletRec) to check: *no new fillet introduced where disallowed*, *minimum thickness maintained*, *bolt-hole neighbors remain intact*, etc. If any feature-level rule is violated (as judged by the network), the variant is quarantined. This supplements geometric checks with learned pattern recognition of valid vs. broken features.  
- **Stable entity identity:** To know if an engineering face (e.g. the bearing face) is “the same” post-edit, we can combine topology tracking with learned descriptors. For example, maintain semantic labels on faces: “BEARING_SEAT”, “HOUSING_MOUNT”, etc. After each edit, use a GNN to re-label faces. The face continuing to match the original label with minimal geometry change (axis, diameter tolerance) is our “identity trace” for that feature. If the label disappears or jumps, that signals an invisible edit error. This elevates “protected-interface comparison” to a full identity system, aided by neural face classification from B-rep graphs.  
- **Feature-conditioned physics mapping:** When topology changes, physics entities (loads, constraints) must remap. Here a graph-based matching can help. For each load/BC on a face in the original, use the B-rep graph to find *similar* face(s) in the variant. Similarity can be judged by shape descriptors or GNN embeddings. For ambiguous cases (face splits/merges), assign a confidence score. Those below a threshold trigger “rebuild load” or block the variant. This semantic mapping complements the rule-based approach (e.g. map face by vertex overlap), adding a learned notion of which target face is most semantically equivalent.  
- **Frozen interfaces & mesh coupling:** The “frozen island” idea means we keep CAD faces (and their meshes) for key interfaces. To enforce this, we treat the frozen patch as a subgraph that must embed conformally. Meshing at the interface can then be done with a conformal (or MPC) coupling. Here, graph methods can again help classify which boundary surfaces are frozen vs mutable, and to set up mesh ties. For example, run a GNN to identify all faces belonging to the bearing boss, then mark them frozen. The mesh generator then uses an imprint/merge or tie on that subgraph. We would create an explicit “interface coupling module” in the pipeline to apply the appropriate mesh rule for each frozen patch.  
- **Manufacturing constraints as features:** Many manufacturability rules (wall thickness, draft, fillet radius) can be phrased as graph attributes. For instance, minimum thickness between parallel faces can be checked by sampling or computing narrow graph distances. A feature network can identify accidental thin-sheet features or undercuts that violate casting rules. Thus, learned classification can enforce constraints like “no rib crossing core-line” by flagging unusual face adjacency patterns. However, we still need explicit numeric rules (wall-thickness maps, draft-angle checks) – but detection networks can catch complex exceptions that simple rules might miss.  
- **Search & optimization integration:** The plan suggests using CP-SAT for combinatorics. To add continuous search, we will train a *surrogate* model on initial runs to predict viability or objective quality from design parameters. Graph neural features (from the CAD graph) can feed this model. In each CP-SAT candidate, instead of blindly discretizing all continuous dims, we can do a quick gradient-free local search (or Bayesian optimization) on a subspace of parameters that significantly affect stress or mass. Techniques from *cadjoint* hint that one could even take shape gradients (though cadjoint is more prototype for implicit shapes). At minimum, we’ll use the ML features to pre-screen good regions of parameter space.  
- **Failure memory & surrogate:** As variants fail (geometry/mesh/solver) we record their “failure signature” (which face or operator caused it, and the GNN-encoded geometry at failure). A classifier (or regression) can learn patterns of likely failure. This becomes a coarse *feasibility surrogate*: given a candidate design (represented by its edit-graph or latent code), predict P(complete). That way, the planner avoids doomed regions of design space, improving overall yield.  
- **Dataset splitting for surrogates:** We will group our variants by “architectural family” (the sequence of operators applied). Train/test splits will hold out entire families or unseen operator combinations to test generalization. For continuous parameters, we will test in regions not seen during training (e.g. extrapolation in rib thickness). This avoids leaking trivial variants that only differ by small tweaks. SketchGraphs’ approach of having train/val/test splits of construction sequences can guide our splitting strategy.  
- **Engineering qualification post-solve:** Every solver result must pass an “engineering sanity check.” ML can augment this: e.g. a surrogate for stress distribution shape (via graph features of the result) could flag nonphysical patterns. Meanwhile we will explicitly verify: load directions, no inverted modes, consistent energy balance, etc. We can store each variant’s “truth model” – which geometric features must maintain nominal values – and check them using a combination of scripts and learned detectors.  

# Experimental Plan for 100–200 Variants

1. **Setup baseline and toolchain:** Start with the approved GRC housing baseline. Implement the CAD operator library (from your plan) in a robust CAD kernel (OpenCASCADE via PythonOCC or a commercial API). Integrate the feature-detection models: load pretrained AAGNet/FilletRec/BRepMFR (or train them quickly on available data) so we can label any new CAD. Set up meshing tools with the frozen interfaces and coupling rules.

2. **Define parameterized edits:** Catalog the plan’s edit sequence (add/subtract ribs, holes, fillets, etc.) with parameters. Encode each operator formally (with input references, param domains as feedback recommended). This becomes the agent’s action space. 

3. **Initial sampling & calibration:** Perform a batch (e.g. 20–30) of random or low-discrepancy samples of the design space (different parameter values and edit combinations). For each variant, run the full pipeline (CAD edit → mesh → CAE solver). Check reproduction: first run the solver on the *unaltered baseline* and compare to known baseline response (at multiple points and fields) to calibrate tolerances. This yields target bands for displacements, stresses, etc., forming the “reproduction certificate” thresholds. Also record which variants succeed or fail, building up a dataset of geometry/success labels.

4. **Train initial surrogate & failure model:** Use the data from step 3 to train a simple regression or classification model (e.g. random forest or small NN) that maps the variant parameters (and possibly GNN-encoded geometry summary) to outcomes: “mesh success” and “max stress”. Also train a separate classifier for the failure mode (geometry error vs. solver break vs. design reject). 

5. **Iterative generation loop:** Now run in rounds. In each round:
   - **Proposal:** Use CP-SAT to generate 50–100 new candidates (architectural choices + discrete grids of parameters). Filter these through the surrogate to drop very likely failures (based on learned failure model). For continuous dims, refine promising candidates via a local optimizer or sampling around them guided by surrogate gradients. 
   - **Verify & simulate:** For the remaining 100–200 candidates, execute the CAD edits, apply mesh, and run CAE. Use the feature detectors to enforce operator contracts and design contract compliance (any violation means “quarantine” – skip solver). Solve the FEA for the rest, and label each as pass/fail. 
   - **Update models:** Retrain/update the surrogate and failure predictors with the new data, improving predictions. Track coverage of design space vs yield. 
   - **Stop criterion:** Continue until we accumulate ~100–200 **accepted** (engineering-qualified) records that meet the load/strength criteria. 

6. **Quality checks:** Finally, for a subset (say 10%) of accepted variants, perform double-check CAE with a possibly higher-fidelity solver or mesh to ensure our pipeline fidelity. Report statistics: geometry yield (successful variants vs attempts), solver yield, and design coverage of key dimensions (rib heights, wall thicknesses, etc.).

# Resources, Timeline, and Metrics

- **Team/Tools:** A small team (2–3 engineers) to integrate CAD and ML pipelines. Use PythonOCC or a commercial CAD API, plus PyTorch/TensorFlow for ML. Required ML models (AAGNet, FilletRec, BrepMFR) are open-source and can run on GPUs; HNC-CAD code (PyTorch) could be used to generate a few creative designs if needed. A workflow manager (e.g. Airflow or custom agent) will orchestrate the CAM jobs.

- **Compute:** One or more GPU workstations (24GB VRAM) for training/feature inference. A compute cluster or cloud (40+ CPU cores, ~200GB RAM total) for parallel CAE runs. We estimate ~100–200 full FEA solves; if each takes ~1–2 hours, parallelizing on 50 cores can finish runs in a few hours per batch. Using containerized environments ensures reproducibility (every CAD/solver version is logged).

- **Timeline:** 
  - Month 1–2: Set up CAD environment, implement operators, integrate PythonOCC + occwl graph builder. Install and test ML models on baseline geometry (sanity-check feature labels).  
  - Month 3–4: Baseline reproduction runs and calibration. Gather initial dataset of ~20 variants. Train surrogates.  
  - Month 5–8: Iterative generation rounds (3–4 rounds). Each round ~2 weeks: propose, simulate, retrain. Fine-tune operator contracts based on initial failures.  
  - Month 9–10: Final validation batch, engineering review, and analysis. 

- **Success metrics:** We aim for ≥90% geometry yield (variants not filtered out) and ≥95% solver yield on “approved envelope” inputs. Importantly, we will also monitor **coverage** of the design space: e.g. what percentage of the intended variation ranges (rib heights, wall thicknesses, fillet radii) have been explored in accepted designs. We will track surrogate accuracy (e.g. RMSE on stress prediction), and final use-case metrics (e.g. mass reduction vs baseline, bearing stress margin). The campaign is successful if we produce 100–200 *distinct, validated* gearbox variants meeting all CAD/CAE criteria, along with a trained surrogate that can predict outcomes for future queries.

By combining deterministic CAD operations with these ML components – graph-based feature checks, learned surrogates, and generative proposals – we create a robust “smart design factory.” The pipeline enforces formal contracts (geometry, physics, manufacturability) but also learns from data (failures and successes) to improve search efficiency. We will document each variant’s provenance (CAD version, operator sequence, random seed) so all results are reproducible.
